- The Wheels CLI could send state-changing commands, console code and the application's reload password to a local server it had not verified as the current project's own, for example another application listening on the project's configured port or on a common development port. Commands that change state or evaluate code (`migrate` write actions, `seed`, `db reset`, `reload`, `console`, `jobs work`, `generate admin`, `coverage`, `test`, `browser test`) now require the server this project started with `wheels start` (or `wheels engines rustcfml start`), and refuse otherwise, naming the port. The server is verified as that registered process, the only process listening on its port, and, for every request, the process that accepted the CLI's connection before anything is sent on it. Requests go to the address the server binds rather than resolving `localhost`; `console` never falls back to probing ports; read-only commands that use an unverified server say so. The CLI now sends the reload password in an `X-Wheels-Reload-Password` request header instead of the URL query string, keeping it out of access and proxy logs. `public/Application.cfc` accepts the header alongside the existing `?password=` parameter. Existing apps should copy the header-mapping block (the `X-Wheels-Reload-Password` block near the top of `onRequestStart()`, before the reload lock) from the current template into the same place in their own `public/Application.cfc`; until they do, the CLI falls back to the query string for that project's own verified server only and prints a notice. `.env` detection now reads only a line-start `PORT` and `WHEELS_RELOAD_PASSWORD`/`RELOAD_PASSWORD`, not another key that ends the same way such as `DB_PORT` (GHSA-x3cm-2j3q-jgg4)
